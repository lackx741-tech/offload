01 / What ST3 does

Product purpose

ST3 is documented as a web3 operational dashboard, contract/ABI configuration surface, frontpage/CTA builder, and JavaScript bundle compiler. Its root Next.js application lets an operator configure contracts, wallet/modal behavior, strategies, and app branding, then generate a deployable client bundle.

The active root product is not merely a landing page. It combines an authenticated admin surface, configuration APIs, contract registry, compile pipeline, generated-script storage, wallet-provider integrations, operational pages, Telegram webhook support, and worker/service preparation.

Repository reality

The repository also contains older notes and companion projects: standalone wallet modals, affiliate/admin UIs, a web3 platform compiler, a Telegram bot, an indexer, a test dapp, a Vercel demo, a Python Telegram client, and contract ABI/deployment material.

Therefore ST3 should be understood as a root control plane plus a portfolio of attached experiments and services, not one homogeneous app.

14 / Dead-code and duplicate analysis

ST3 is not dead code. The root has a coherent Next.js app, package scripts, routes, configuration stores, generator libraries, tests, and deployment documentation.

The likely maintenance/dead-code candidates are not the root product but the accumulated ecosystem:

  • Older loose root Markdown files that make “production ready” claims inconsistent with current docs.
  • Parallel standalone modal implementations: custom, Rainbow, Reown, and Vercel.
  • Multiple affiliate/admin implementations: root routes, affiliate-app, and Affliate and admin.
  • Duplicated ABI locations: abi/, contracts json/, and embedded config copies.
  • Nested indexer/compiler/bot services whose root integration is not demonstrated.
  • Generated directories such as .next, .builds, and generated scripts, which are artifacts rather than source projects.

Definitive dead-code classification requires import graphs, CI references, commit history, and a clean build; filenames alone are insufficient.

Why TrustContract is not active

The registry source explicitly states that drainer entries are preserved but not ABI-wired. The active backend resolver returns only four names: stealth-exchange, permit2-executor, erc2612-executor, and batch-multicall. The strategy layer calls that resolver, so TrustContract can be listed and inspected but cannot be selected by the active execution binding path.

What “wired” would mean in the report

A contract is fully wired only when the repository shows: registry metadata, an active backend resolver entry, a strategy preset with exact ABI argument mapping, configuration/UI selection, route compatibility, tests, and verified deployment/network metadata. TrustContract currently satisfies the first two catalog-related parts only; it does not satisfy the active-backend and strategy-binding parts.

18 / Contract wiring conclusion

ST3 contains more contract artifacts than it currently exposes through active strategy execution. That is why seeing TrustContract.json does not mean the contract is connected to the runtime. The current architecture intentionally has a catalog layer and a narrower active execution layer.

For project intelligence purposes, TrustContract should remain marked catalogued / inactive until its intended, consent-based behavior, exact function schema, deployment identity, route binding, tests, and operational ownership are independently verified.

19 / Final conclusion

ST3 is a substantial, operationally oriented web3 control plane with a real root application and a broad surrounding ecosystem. The strongest current product path is:

Admin loginauthenticated control→Contract + ABIregistry/config→Frontpage configCTA/modal mapping→Compilegenerated bundle→Test/operatelogs, workers, providers

The repository is operationally rich but not uniformly production-verified. Its main uncertainty is not whether ST3 exists—it clearly does—but which nested services and execution branches are canonical, currently wired, tested, and safe to expose.
