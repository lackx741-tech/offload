# Current runtime report

Evidence is limited to repository code and checked-in deployment configuration; it does not assert live deployment state.

1. **What starts the application?** Development uses `npm run dev` → `scripts/dev.mjs` → Next dev server (`package.json:13`; `scripts/dev.mjs:22–58`). The Docker production image runs the standalone Next `server.js` (`Dockerfile:53–65`).
2. **What starts workers?** `npm run workers` runs `workers/run-all.ts`, loads environment files and imports the Telegram, compile, notify and relay workers (`package.json:24`; `workers/run-all.ts:6–17`). Individual worker scripts are also declared at `package.json:20–23`.
3. **What dashboard routes are active?** App Router pages exist for the routes enumerated in `ENTRYPOINTS.md`; root layout wraps children with theme, Reown, tooltip, layout, hydration and toaster providers (`src/app/layout.tsx:32–60`). Middleware enforces its cookie check except allowlisted paths (`src/middleware.ts:7–35`).
4. **What API routes are active?** 45 API route modules exist under `src/app/api` (list in `ENTRYPOINTS.md`). The queue, compile, Telegram, generated script, project and contract paths are backed by explicit request handlers cited in their corresponding flow reports.
5. **Where is configuration persisted?** Compile configuration and operational configuration are JSON files in `data/`, managed by `compile-config-store.ts:38–89` and `operational-config-store.ts:31–79`. Frontpage configuration uses `frontpage-config-store.ts:5–62`. Affiliate projects/configs and Telegram bot sessions use Redis (`projects.ts:99–139,236–280`; `telegram-bot-store.ts:16–69`). Browser-only frontpage imports/config also use `localStorage` (`src/app/frontpage/page.tsx`; `src/app/frontpage/runtime/page.tsx`).
6. **How are projects represented?** `AffiliateProject` and related config types are in `src/lib/projects.ts:28–62`; IDs have `aff_` prefix and Redis stores project and config records (`:64–89,99–139,236–280`).
7. **How are contracts discovered?** Static contract selection uses `CONTRACT_REGISTRY` (`src/lib/contract-registry.ts:48–73`). Separately, `/api/contracts` scans known filesystem roots, including `abi/` and `contracts json/` (`src/app/api/contracts/route.ts:63–114`).
8. **How are ABIs loaded?** Static registry imports JSON from top-level `abi/` and three artifact files from `contracts json/` (`src/lib/contract-registry.ts:6–26`). Runtime artifact APIs read JSON from disk and extract `.abi`, `output.abi`, or `artifact.abi` (`src/app/api/contracts/[id]/route.ts:14–20,59–88`). Imported custom ABIs persist as `customContracts` in operational config (`src/app/api/contracts/import/route.ts:35–50`).
9. **How are actions/functions selected?** Contract UI selects a registry contract/function and updates contract/function binding and strategy in the Zustand store (`src/components/compile/contract-tab.tsx:28–65`). Registry-derived bindings are assembled by `standard-function-bindings.ts:9–69,82–117`. Frontpage `contractWrite` actions retain method ABI/args, converted by `contract-actions.ts:27–57`.
10. **What triggers compilation?** Compile page’s output component calls `POST /api/compile` or directly generates a drainer bundle (`src/components/compile/compile-output.tsx:203–250`). Additional entrypoints are affiliate APIs, project compile route, frontpage compile API, `GET /api/sdk`, `/api/script`, and Telegram `/compile` (`ENTRYPOINTS.md`; `SCRIPT_GENERATION_PIPELINE.md`).
11. **What actually generates scripts?** `generateSDKBundle`, `generateSolanaBundle`, `generateTronBundle`, `generateUniversalBundle`/`generateDrainerBundle`, `compileFrontpageScript`, `generateDrainerScript`/`generateAdvancedDrainerScript`/`generateDrainerPage`, and `generateWeb3RewardsScript` have implementation code. Caller status and output modes are in `GENERATED_OUTPUTS.md`.
12. **What types of scripts are generated?** Executable JavaScript: SDK/EVM bundle, Solana/Tron runtime bundles, contract-action frontpage bundle, drainer JavaScript and Web3 rewards script; `generateDrainerPage` also creates HTML (`GENERATED_OUTPUTS.md`).
13. **Where are generated scripts stored?** `saveScriptBuild` writes to `.builds/` with a temporary file and rename (`src/lib/script-build-store.ts:33–37,100–133`). Checked-in or deployed static files also exist under `public/generated-scripts/`. `saveScriptBuild` does not write that public directory; its returned URL is a URL string (`:63–65,112–133`).
14. **How are scripts retrieved?** Inline/API-generated output is returned directly by `/api/compile`, `/api/frontpage/compile`, `/api/sdk`, `/api/affiliate/compile`, and `/api/script`. Static `public/generated-scripts/` is served by Next static-file behavior. Build-store records link to a fixed `/generated-scripts/...` URL but `.builds` has no mapped route shown in this path; do not equate the two stores (`script-build-store.ts:33,63–65,115–141`).
15. **How does Telegram reach generation?** `/api/telegram/webhook` validates the optional shared secret, then enqueues an inbound job or invokes `processTelegramUpdate` inline (`route.ts:21–45`). Worker dispatch reaches `/compile`; `handleCompileCommand` enqueues compile job and `compile.worker` calls `compileAffiliateProject`, generates/obfuscates/publishes, then optionally sends a completion message (`telegram-bot.ts:795–816`; `compile.worker.ts:57–90`; `affiliate-compile.ts:32–112`).
16. **Which queues are actually active?** Queue definitions and workers exist for inbound/outbound Telegram, compile, notify and relay (`src/lib/queues/index.ts:14–20`; `workers/*.worker.ts`). Proven producers in application call sites: inbound Telegram, compile, notify. Relay and outbound Telegram producers have definitions but no discovered application call sites (`QUEUE_GRAPH.md`).
17. **Which implementations are disconnected?** Relay enqueue producer, outbound Telegram producer, `generateWeb3RewardsScript`/bundle as an independent generator, drainer-script API unless external caller, and some separate repo packages have no proven caller/consumer in the root app. Exact evidence and classifications are in `DISCONNECTED_IMPLEMENTATIONS.md`.
18. **Which duplicate systems exist?** There are static and dynamic bundle paths (`public/generated-scripts`, `.builds`, `/api/sdk`, `/api/script`); multiple config stores (compile, operational, frontpage, affiliate); duplicated contract artifact sources (`abi/`, `contracts json/`, registry, runtime discovery); root standalone/package/demo apps; and current/legacy/snapshot source copies. Their readers are differentiated in corresponding reports.
19. **Which runtime paths are synchronous?** Normal `POST /api/compile` is synchronous unless `queue:true` or `async:true`; relay batch is synchronous; affiliate compile API and project compile GET compile inline; `/api/sdk` and `/api/script` generate during request; frontpage compile generates then stores before response.
20. **Which paths are asynchronous?** Queue-backed compile/Telegram/notify when queue mode is enabled; Telegram webhook returns after enqueue. `GET /api/compile/status/[jobId]` polls compile state. Some telemetry notifications/Kafka publishes are best-effort, non-blocking calls in their route.

## Runtime boundaries

- BullMQ uses Redis via `REDIS_URL` (default `redis://localhost:6379`) and is disabled only when `DISABLE_QUEUES` is one of `1|true|yes` (`src/lib/queues/index.ts:24–57`).
- Kafka event bus is conditional on `KAFKA_BROKERS`; its fallback path is in `src/lib/kafka.ts:41–100`. The relay route publishes `RELAY_EXECUTED`; dynamic script loads publish `CONTRACT_CALLED` (`src/app/api/relay/batch/route.ts:354–369`; `src/app/api/script/route.ts:66–79`).
- Indexer is separately declared in Compose and has its own polling loop (`services/indexer/index.mjs:12–17,152–196`).
- `DISCONNECTED`, `LEGACY`, `UNKNOWN` in the audit refer to proven static-reference status, not an assertion about historical or externally provisioned usage.
